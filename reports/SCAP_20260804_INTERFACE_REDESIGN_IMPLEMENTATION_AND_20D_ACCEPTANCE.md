本次结果仍为 `exploratory`，`formal_eligible=False`。20 日小窗只证明链路、约束和保存，不证明收益、回撤或样本外有效性。

## 2. 实施后的唯一语义链

决策顺序固定为：

`事实状态 → 产品政策 → 强制安全动作后投影 → 当日可行边界 → 恢复授权 → 唯一整数 ActionPlan → 执行硬事实复核 → 成交/账户 → 审计与 Web`

关键语义不再复用：

- `policy_holding_floor / policy_exposure_lower`：产品政策原值，不能被候选、现金或优化器覆盖。
- `post_mandatory_*`：安全退出等必须动作执行后的投影事实。
- `conditional_holding_floor / conditional_exposure_floor`：只由成本后正价值且整手可行的候选、现金与硬上限支撑的当日硬下界。
- `daily_effective_*_ceiling`：当日事实可执行硬上限。
- `planned_holding_count / projected_exposure`：唯一 ActionPlan 的结果。
- `holding_floor_violation_count / exposure_floor_violation`：不可行时显式保存，不得靠改名或覆盖政策值隐藏。
- `selected_position_count`：选中动作涉及的名称数，不再冒充计划后持仓数；旧字段仅作兼容别名。

## 3. 模块级修改与静态金融审查

### 3.1 政策与参数

- `config.py` 建立四状态 `scap_policy_bands`，保存持仓下界/目标、仓位下界/目标/上界与灾难硬顶；增加精确搜索名称数、beam 宽度和人民币财富实质差异阈值。
- `exposure_contract.py` 的 `resolve_policy_band()` 只解析政策，不再把事实可行性写回政策。
- 非有限数、负值、逆序边界和非法资源参数在配置校验时失败关闭。

金融判断：政策值是产品承诺；现金、整手、风险与候选质量只能影响当日可行边界，不能倒写政策历史。

### 3.2 金融容量与计算资源

- `capital_scaling.py` 将交易容量与优化器搜索预算拆开。
- 旧 `risk_feasible_position_cap` 没有独立风险估计证据，明确标记为 `not_independently_estimated_cash_proxy_only`，不再让名字伪装成真实风险模型。
- `exact_max_positions` 与 `beam_width` 只决定计算方法，不再冒充持仓金融上限。

金融判断：硬持仓上限来自产品、现金、整手和已证实风险边界；求解器能搜索多少名称不是风险容量。

### 3.3 强制动作后投影、条件下界与恢复

- 新增 `portfolio_constraint_contract.py`，提供 `PolicyBand`、`MandatoryProjection`、`DeploymentBounds`、`RecoveryAuthorization`。
- Lean 链先投影必须执行的安全卖出，再计算可由正价值候选支撑的条件下界，最后判断是否需要同一 ActionPlan 恢复。
- runner 持久化恢复 episode ID、episode day、当日最大新增名称数、最大买入仓位和截止期；缺口消失后清零，不能每天伪装成全新恢复事件。

金融判断：安全退出优先权保留；恢复不能阻止退出，但必须基于退出后的组合重新计算。负净价值候选不能因为最低持仓目标而获得交易权。

### 3.4 整数 ActionPlan

- 优化器接收最低/目标持仓数、最低/目标仓位、硬上限、现金、整手、成本和人民币 epsilon。
- 排序层级为：硬事实与上下界 → 最小化不可行下界违反 → 人民币财富近优集合 → 目标缺口与有效广度 → 精确稳健财富及成本。
- 1 元人民币 epsilon 只在经济结果实质近似时用于选择更接近政策目标和更分散的方案；不会复活负价值候选。
- ActionPlan 保存 `planned_holding_count`、上下界违反量、epsilon 和目标函数分解。

数学判断：本优化器是离散整数/beam 搜索，不是梯度下降。此前“特殊值导致紊乱”的实际风险来自浮点字典序、单位混用、阈值硬切换和求解器资源参数混入金融约束，本轮分别处理。

### 3.5 执行、保存、审计和 Web

- 执行层只复核现金、整手、交易限制和计划硬仓位顶，不再以软目标加容差二次否决已经授权的 ActionPlan。
- `policy.py` 中 new/add/replacement 订单直接继承 proposal 的 `exposure_delta`，禁止从 `lot_weight` 二次估算。
- 暴露勾稽分别计算政策目标缺口、政策下界缺口、强制动作后下界缺口与计划执行缺口。
- Web 分开显示优化后计划持仓数和选中动作涉及名称数，避免旧字段名误导。

金融判断：市场名义仓位、买入现金需求和交易成本是三个不同量。建议、计划和订单必须使用同一个市场仓位口径，现金账本则独立计入佣金等成本。

## 4. 过程中捕获的真实缺陷

### 4.1 第一次运行：验收合同滞后

`run20260804_121859` 完成 20 日，但旧验收仍硬编码恢复最多 1 个名称/15% NAV，和新“覆盖条件缺口但受正价值候选与硬顶限制”的合同冲突；同时日表未保存动态恢复预算。该运行只保留为缺陷证据。

### 4.2 第二次运行：仓位与现金成本口径混用

`run20260804_123349` 完成 20 日后，验收发现三笔订单比 proposal 授权仓位各高约 0.00032–0.00033。根因是 proposal 用市场名义金额/NAV 计算 `exposure_delta`，订单生成又读取包含现金成本含义的 `lot_weight` 重算。

修复后，第三轮三笔订单分别为：

- 2025-01-20 `sz001326`：0.16135000000000002
- 2025-01-24 `sz301203`：0.15848039640956513
- 2025-02-05 `sz001225`：0.1674216314915579

均与各自 proposal 的 `exposure_delta` 精确一致。第二、三轮日期、持仓数量、NAV 和实际仓位路径最大差异均为 0，说明修复校正了授权/审计口径，没有改变成交经济路径。

## 7. 仍未解决与下一步

1. **60% 产品下界仍未在该窗口实现。** 不是优化器忽略，而是正价值、整手可行候选供给不足且单只一手仓位约 16%。下一步应拆分研究：候选经济收益校准、最低经济订单、单名灾难顶与资金规模/整手颗粒度，不能简单降低净价值门槛。
2. **运行仍慢。** 总流程 742.7 秒；前 13 日无持仓仍逐日执行重因子链。应在逻辑冻结后做 profile，优先检查同日特征读取、重复排序/合并和报告阶段；不得通过降低候选覆盖或改变金融求解边界伪装加速。
3. **出现 pandas `All-NaN slice encountered` 警告。** 未导致非有限保存值，47 个回归与产物扫描均通过，但需要定位到具体滚动统计字段并增加冷启动状态，不能长期静默忽略。
4. **回撤问题尚未由 20 日窗口验证。** 用户指出的回撤是相对历史高水位的持续水下路径，必须在固定身份长窗中同时比较最大回撤、最长水下期、恢复时间、仓位路径和候选可行性；本轮不能声称回撤改善。
5. **正式研究/生产准入仍阻断。** PIT 公司行动、PIT 股票池/行业、完整账户和税务账本、可投资基准、独立审阅与正式复现包尚不完整。

建议下一阶段先做固定身份的 338 日受控消融：仅比较旧接口基线与本接口重构，冻结日期、数据、PIT、资本、成本、因子柜、退出阶段和 profile；随后再独立做性能 profile。不得把不同身份结果当成单变量因果证据。
