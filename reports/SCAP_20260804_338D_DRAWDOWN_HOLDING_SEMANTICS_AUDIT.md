## 1. 审计边界与结论

- 唯一主审计对象：`results/decision_council/scap/cab_c6dae8d4d69c/e4_l1200/v3/run20260804_024413`。
- 样本：2025-01-02 至 2026-05-29，共338个交易日，初始资金20,000元。
- 本报告只读取已保存输出、当前源码调用链和本地 Git 历史；不读取外部数据库，不修改策略代码、历史 run、Git 索引、分支或提交。
- 8月3日 `run20260803_141905` 仅作为相邻运行诊断参考。两次运行的代码指纹/运行身份不同，因此差异能定位机制，不能当作单变量因果实验。

核心结论：8月4日结果变差不是单日冲击变大，而是净值在2025-08-19形成高点后长期无法创新高。最大回撤按历史高水位计算，连续偏弱、反弹参与不足和现金拖累共同把水下期拉长至185个交易日，最终形成 -14.2981% 最大回撤。持仓模块的根本问题也不是某一个阈值太低，而是“最低持仓/最低仓位”没有成为优化器的约束；它们在优化完成后才被计算和展示。与此同时，多项字段名称与实际公式不一致，造成报告、Web和审计模块对同一字段作不同解释。

## 2. 结果为什么更差

| 指标 | 8月3日338日运行 | 8月4日338日运行 | 诊断 |
|---|---:|---:|---|
| 总收益 | 17.2235% | 7.5150% | 收益下降9.71个百分点 |
| 最大回撤 | -9.8570% | -14.2981% | 深度恶化4.44个百分点 |
| 最差单日 | -8.0475% | -3.2288% | 单日冲击反而显著减小 |
| 最长水下期 | 79日 | 185日 | 恶化来自长期未创新高 |
| 平均实际仓位 | 41.20% | 31.78% | 反弹参与不足 |
| 平均持仓数 | 3.115 | 2.405 | 广度进一步下降 |

8月4日最大回撤路径是：2025-08-19净值23,979.695元形成高水位，随后持续处于水下，至2026-04-03降至20,551.046元，最大回撤为 `20551.046 / 23979.695 - 1 = -14.2981%`；截至2026-05-29仍未恢复该高点。该事实支持用户的纠正：问题是高水位之后持续走低和恢复不足，而不是单日损失突然变大。

月度路径也支持相同结论：2025年9月 -3.364%、11月 -0.906%，2025年12月虽月末 +0.951%但月内回撤一度约 -10.286%；2026年3月 -11.597%。2026年4月策略仅 +4.160%，同期基准约 +14.725%，低仓位导致最需要恢复时没有充分参与反弹。全期基准约 +47.7568%，策略仅 +7.5150%。

因此应把回撤分解为三个量，而不能只盯最大回撤深度：

1. 高水位后的累计亏损；
2. 水下持续时间；
3. 上涨日/反弹期因现金和低持仓造成的恢复缺口。

## 4. 参数名、真实公式和决策作用对照

| 当前名称 | 代码/输出里的真实含义 | 是否真正约束优化器 | 问题 |
|---|---|---|---|
| `exposure_gap` | `max(strategic_lower_bound - actual_exposure, 0)` | 仅决定追仓授权/预算 | 不是“目标仓位缺口”；审计模块却按目标减实际重算 |
| `strategic_exposure_gap` | `max(strategic_target - actual_exposure, 0)` | 否，诊断字段 | 与上项同时存在但界面未清晰区分 |
| `holding_shortfall_count` | 实际映射为 `max(soft_target - actual, 0)` | 否 | 名称容易被理解为低于最低持仓的缺口 |
| `minimum_required_holding_count` | 风险状态最低值再受动态上限裁剪，优化后构造 | 否 | 名为 required，实际没有 required 行为 |
| `soft_target_holding_count` | 状态软目标，动态裁剪，优化后展示 | 否 | `capital_scaling.py`明确注释“reporting target, not a minimum constraint” |
| `maximum_allowed_holding_count` | 当日 `effective_position_cap` | 是上限 | 不是稳定产品硬上限，而是经济/候选/搜索等动态最小值 |
| `risk_feasible_position_cap` | 当前直接沿用经济现金容量 | 是动态上限的一部分 | 没有独立组合风险可行性求解，名称夸大含义 |
| `selected_position_count` | 优化器选中 action 涉及的名称数 | 间接 | 不是计划后总持仓；Web却显示“计划持仓数” |
| `optimizer_planned_holding_count` | ActionPlan目标 lots 中的真实计划后持仓数 | 计划事实 | 这才应作为“计划持仓数”显示 |
| `attainable_exposure_ceiling` | `min(max(lot_feasible_target_exposure, actual_exposure), 1)`一类描述值 | 否 | 不是联合优化后的严格可达前沿 |
| `catchup_rate` | 允许时固定返回1.0，否则0.0 | 否 | `_catchup_rate()`虽计算却未写入返回值，实为授权布尔量 |
| `recovery_window_sessions` | 配置值被传递并保存 | 未发现状态消费 | 不能据此宣称已实现“五日恢复窗口” |
| `accuracy_multiplier` | 计算并保存的诊断量 | 未进入预算/优化器 | 名字暗示会缩放仓位，实际没有 |
| `breadth_near_optimal_tolerance_amount` | 授权对象中保存 | 优化器未消费 | 当前属于死参数 |
| `STRATEGIC_EXPOSURE_NORMAL=0.90` | 配置表中的值 | 当前主调用链未消费 | 活跃状态映射在 `resolve_strategic_exposure_band()` 中硬编码目标0.75、下界0.60、上界0.85、硬顶0.90 |

直接输出证据：`governance_exposure_reconciliation.csv` 的338行全部存在非零语义重算误差，最大约0.25、平均绝对误差约0.1471。原因是审计端把 `exposure_gap` 当成目标缺口，而生产端保存的是下界缺口。这不是数据随机误差，而是跨模块公式合同不一致。

此外，`selected_position_count` 与 `optimizer_planned_holding_count` 在143/338日不相等；前者在145个“实际仍持仓”的交易日为0。用它汇总“平均计划持仓数”会系统性低估计划组合规模。

## 5. 为什么最低数量没有维持、最高数量很少达到

当前顺序实质是：先由候选经济性和搜索容量形成动态上限，整数优化器只检查最终名称数不超过 `max_positions`，然后 runner 再构造最低/软目标/最大值语义用于报告。优化器 `_plan_key()` 没有接收最低持仓数或最低仓位，也没有 `K >= K_min`、`E >= E_min` 约束。

所以：

- “最低持仓”只是运行后发现不足的诊断值，不会阻止优化器选择空计划；
- “最高持仓”每天随经济容量、候选数量和搜索上限变化，不是先验稳定硬边界；
- 软目标既不形成约束，也没有在“收益近似相同”的候选计划之间获得可靠优先级；
- 追仓最多一天增加1个新名称、最多增加15%仓位，而退出可一次清空多只，恢复速度天然小于去风险速度。

典型路径发生在2026-03-23：此前4只持仓、实际仓位约49.07%，弱状态下界40%，因此按交易前仓位判定不需要追仓；同一计划却触发4笔 `loss_containment` 强制退出，计划持仓直接变为0。系统没有在强制退出后的投影组合上重新计算最低持仓和追仓授权，只能从下一日开始每天最多补1只。安全退出本身应保留，错误在于“先用退出前仓位判断无需补仓，再在同一计划中清空”。

全期46次买入、45次已平仓，净增加仅1只，说明新增数量大体只抵消退出，无法形成稳定的最低持仓。46次买入全部为C级授权，其中37次属于 `size_style` 论点，32次集中于301前缀；低总仓位并不等于低相关性风险，少量持仓仍高度集中于同一风格/板块。

## 6. 数学与特殊值问题

当前优化器不是梯度下降，而是整数穷举/beam search。用户所说“特殊值使公式陷入梯度下降、紊乱”的现象是对的，但精确机制是离散目标的断崖和排序不连续：

1. 计划采用精确浮点字典序：先比较稳健目标，再比较部署缺口、广度、期望收益、下行、成本。第一项即使只差几分钱，也会完全压倒后面的持仓恢复和广度，而配置的“近优容差”没有参与比较。
2. 成本占保守毛收益比例在毛收益接近0时高度不稳定，并在60%处硬切。258个新入场提案中111个超过60%，成本占比中位数约50.97%、75分位约83.97%。应在分母附近显式处理，不应把近零毛收益的比率当连续、稳定度量。
3. `max_positions` 从5变6时，求解器由精确穷举切到 beam；本次有81日上限大于5、41日实际使用beam，上限跨越5/6边界37次。一个持仓名额变化会同时改变求解算法和最优性保证。
4. 状态仓位带从正常 `(目标75%, 下界60%, 最低3, 软目标4)` 跳到弱势 `(55%, 40%, 2, 3)`，再跳到高风险 `(25%, 0%, 0, 2)`；本次状态切换23次。没有充分滞回时，持仓目标和追仓权限会离散跳变。
5. 2026-05-15被选计划的最终稳健目标仅约0.4478元，场景风险惩罚约9.527元，说明存在接近零边界的脆弱入选；精确字典序对微小估计误差很敏感。

保存输出的关键提案数值未发现 NaN/Inf，这说明本次主要不是非有限数直接污染，而是有限但靠近阈值的数触发了离散分支。

## 7. 与 Git 留存版本的只读比较

本地 HEAD 为2026-08-02的 `1749924`。只读 diff 显示当前候选上限由24降为12，精确求解最大持仓由8降为5，beam宽度由512降为256。这会缩小搜索空间、提前切换近似算法，能够解释速度仍慢但解质量可能下降的一部分现象。

旧版曾把 `NAV × 现金缺口惩罚率 × 部署缺口` 直接从目标中扣除；当前删除该金额惩罚，部署缺口只作字典序次级比较。不能直接恢复旧惩罚，因为它可能强买负边际候选。正确办法是：先满足“在正净价值候选可行范围内的条件硬下界”，再在可行集合内优化财富和广度。

Git版本同样把软目标注明为报告字段，并非最低约束，因此“最低持仓未被执行”不是8月4日单独新产生的问题；8月4日修改使低仓位后果更明显，但不应把旧版当作自动正确答案。Git只能作为受控消融基线，不能盲目回滚。

## 8. 建议的重新设计（本轮不实施）

### 8.1 先定义不可混淆的硬边界

先于优化器计算并冻结：

- 产品硬上限 `K_product_max`；
- 整手/现金/合法性可行上限 `K_feasible_max`；
- 最终硬上限 `K_hard_max = min(K_product_max, K_feasible_max, K_risk_structural_max)`；
- 仓位硬上限 `E_hard_max`，包含无杠杆、现金、停牌/涨跌停可执行性和安全风险上限。

搜索候选数、beam宽度属于计算资源参数，必须与金融硬上限分开命名和报告，不能继续混进 `maximum_allowed_holding_count`。

### 8.2 最低约束必须是“条件可行硬下界”

强制安全退出先进入计划，按退出后的投影组合重新计算：

`K_floor = min(K_policy_min, K_hard_max, K_post_exit + N_positive_feasible_candidates)`

`E_floor = min(E_policy_lower, E_hard_max, E_positive_feasible_ceiling)`

优化器必须满足 `K_floor <= K_final <= K_hard_max`、`E_floor <= E_final <= E_hard_max`。如果正净价值、整手可买候选不足，应保存“结构性不足”及原因，不能把政策最低值偷偷改小，也不能为了凑数量买入负净价值标的。

### 8.3 固定执行顺序

1. 读取事实持仓、现金和可交易状态；
2. 生成不可取消的安全退出；
3. 形成退出后投影持仓/现金/仓位；
4. 基于投影状态计算条件最低、硬上限和恢复权限；
5. 在同一个整数ActionPlan中联合选择替代与新增；
6. 先验证硬约束，再比较软目标；
7. 保存事实、政策、可行性、计划和实际六层字段，不允许相互覆盖。

### 8.4 分层目标代替精确浮点字典序

- P0：安全、交易规则、现金、整手和硬风险约束；
- P1：最小化条件可行的持仓/仓位下界违反；
- P2：最大化成本后保守增量财富；使用人民币最小实质差异 `epsilon_amount`，不比较无意义的微小浮点差；
- P3：在财富近优集合内最大化论点、板块和风险贡献广度；
- P4：最小化成本、换手和未部署缺口。

### 8.5 必须改名或纠正实现

- `exposure_gap` → `lower_bound_exposure_shortfall`；
- `holding_shortfall_count` → `soft_target_holding_shortfall`；
- `maximum_allowed_holding_count` → `daily_effective_position_cap`；另增 `product_hard_position_cap`；
- Web“计划持仓数”改读 `optimizer_planned_holding_count`；
- `risk_feasible_position_cap` 在真正做风险可行计算前删除或改名；
- `catchup_rate` 改为 `catchup_authorized`，或真正返回 `_catchup_rate()`并进入预算；
- 未消费的 `accuracy_multiplier`、`recovery_window_sessions`、近优容差要么接通，要么消融删除。

## 9. 施工前的测试与消融矩阵

必须固定日期、数据/PIT快照、资金、成本、因子柜、profile、随机性和报告代码，禁止把不同身份运行直接当因果对照。

单元/性质测试至少覆盖：毛收益为0及正负极小值；成本占比在60%上下 `epsilon`；最大持仓5与6；无候选；同日4只强制退出；实际仓位刚好位于下界两侧；NaN/Inf；最低等于最高；现金只够一手；状态带反复切换；安全退出后同日替代；计划/成交跨日。

建议依次消融：

1. A：冻结的 Git 基线，仅作只读参照；
2. B：只修字段语义和审计，不改变交易；
3. C：加入退出后条件硬下界；
4. D：加入人民币近优容差和分层目标；
5. E：单独恢复候选数/精确求解边界；
6. F：单独测试恢复速度与五日闭环。

验收不仅看收益和最大回撤，还必须看：最大回撤持续期、恢复速度、低于条件最低的天数、满足候选条件却选0的天数、达到硬上限比例、上涨日捕获、现金拖累、板块/论点/风险贡献集中度、运行耗时和求解器一致性。

## 10. 最终判断

8月4日退化是一个调用链问题，不是单一参数问题：动态上限、事后最低值、退出前追仓判断、每天最多补1只、成本比例硬门、精确浮点字典序和5/6持仓求解器切换共同作用。其表面结果是低持仓、低仓位；深层结果是高水位后无法参加足够反弹，水下期从79日拉长至185日。

当前版本不能声称已经实现“最低/最高持仓硬约束 + 软目标”。它只可靠实现了若干上限和安全退出，最低值及多个恢复参数主要停留在诊断/记录层。建议先完成字段语义单一化和受控消融，再改优化器；在此之前研究门、生产门应继续保持 blocked。
